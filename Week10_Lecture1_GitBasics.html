Imagine This…

You ran an analysis a few months ago. A classmate asks for your code. You find three files:

  • analysis.R
  • analysis_FINAL.R
  • analysis_FINAL_v2_useThisOne.R

Which one is actually correct? Do you remember what changed between them? Could you prove it to someone else?

This is the problem version control solves.

What Is Version Control?

Like “Track Changes” in Google Docs or Word — but for an entire project (code, data, figures, writeups) instead of one document.

It gives you:

  • A complete history of every saved change
  • The ability to go back to any earlier point
  • A way to share your work so others see the same version you do

(10–18 min)

Vocabulary: The Core Five

  • Repository (repo): a project folder that Git is tracking, including its entire history
  • Commit: a labeled snapshot of your repo at one point in time
  • Remote: a copy of your repo hosted elsewhere (for us, on GitHub)
  • Push: send your local commits up to the remote
  • Pull: bring commits from the remote down to your machine

The Big Picture

Committing happens locally and costs nothing. Pushing is the only step that touches GitHub.

(26–38 min)

Wait — Where’s My Pretty Report?

You’ll notice GitHub shows demo.qmd as plain source code, not the rendered report you saw in RStudio.

  • Why: GitHub’s file viewer displays file contents — it doesn’t run code or execute HTML for you. That’s a deliberate security choice, not a bug.
  • Even the .html file Quarto renders will show up as raw code on GitHub, not as a live webpage.

To actually publish the rendered page: pushes your rendered HTML to a gh-pages branch in a public repo.

Common Hiccups

  • “Nothing to commit” — did you save the file first?
  • Push fails / asks for a password — your token may not be stored; re-run gitcreds::gitcreds_set()
  • Can’t find the Git tab in RStudio — close and reopen the Project after enabling Git
  • use_github() errors about an existing repo — pick a new repo name, or delete the old one on GitHub first
